# Tests And Evidence

Read the target repository's validation contract for its gates, and the owning domain spec for the expected values, before adding or changing a test. [references/repository-facts.md](references/repository-facts.md) names both for each repository. This skill applies in every repository; the repository's `AGENTS.md` and `Specs/` win on any conflict. Design rules for hot paths, budgets, and paired baselines are in [performance-resources](../performance-resources/SKILL.md); this skill says how to prove them.

## Writing A Test

- **Names.** Native test files use contextual `Scope.Tests.Behavior.cpp/.h` names. Each assertion checks one observable fact and is named `suite.case`; the runner prints `PASS`/`FAIL` lines and returns nonzero on failure.
- **Independent expectations.** Expected values never come from the code under test. Goldens are independent numeric expectations with their tolerance written into the owning spec table. Behavior with no legacy counterpart uses the independent reference that its owning spec names. A golden changes only together with its owning spec.
- **Diagnosable failures.** On failure print the actual values, so a difference between WARP and hardware, or between machines, can be read from the `test.ps1` output.
- **Negative cases** assert the exact status code, not just failure.
- **No time in tests.** Never sleep, poll, or rely on wall-clock timing in a test; a delay a capture needs lives in the application, not in the test. Worker tests use serial coordinate formulas and event-gated state transitions; a failure timeout detects a deadlock and never asserts a performance threshold. The one exception is state that has no event to wait on, such as asynchronous file or lease cleanup seen from outside the process: poll it to a bounded quiet point, retry transient observation errors, and report the terminal state ([references/patterns.md](references/patterns.md#shared-process-suites)).
- **Fixtures** are hand-written text checked in beside the suite; binary assets are generated by the test so binaries are not committed. Remove stale files before writing. A fixture that overrides fields of a JSON document injects the overrides first, because `yyjson`'s lookup returns the first occurrence of a key ([yyjson](../yyjson/SKILL.md)).
- **GPU tests** use the smallest document that shows the behavior and point sampling unless the case is about sampling, and read the pixels back.
- **A test process never waits on a dialog.** Every suite's `wmain` first routes CRT and STL failure reports away from dialogs, so a failed check ends the run with its report and exit code, and an abort, fast-fail, or crash opens no Windows Error Reporting dialog. A new suite does the same and answers `--failure-report-self-test`, which the repository's tooling tests run for every suite.
- **A hidden self-test owns its keyboard.** Windows writes every physical key transition into each thread's key state at once, the hidden self-test window's included, so a direct `GetKeyState` / `GetKeyboardState` read lets the user's typing fail a step. Where a self-test drives keyboard input, input code reads modifiers from an application-owned keyboard state and the driver writes that state.
- **Sanitizers.** ASan Debug runs the same test executables as the other profiles.

## Hidden, Non-Activating Runs

- Drive public controls and the same application commands as the user through a hidden, non-activating window.
- Ordinary tests never acquire the clipboard, the foreground, or the cursor. A test that needs them is an interactive test: it runs only with the user's agreement at the time, under the repository's interactive desktop lease ([Shared-Engineering-Policies.md](../../../wiki/Shared-Engineering-Policies.md#5-scoped-testing--qualification-test-changesps1)).
- Capture the application's own render through its harness capture switch, never the desktop, and never with Computer Use or a manual screenshot. GUI images come from non-activating synthetic harness fixtures.

## Allowed Write Locations Only (Fail Closed)

- **Critical Normative Rule**: Every test executable, harness, capture driver, and script **DOES NOT HAVE THE RIGHT** to create, modify, or delete files outside explicitly authorized locations ([Shared-Engineering-Policies.md](../../../wiki/Shared-Engineering-Policies.md#6-critical-normative-rule-allowed-write-locations-only-fail-closed)):
  1. The owning repository working tree and repository-local `.build/` (never committed);
  2. An explicitly owner-authorized `<Project>.Perf` drive-root workspace carrying its verified runner ownership marker (or `D:\Archive\RedSalamanders-20261117`);
  3. An explicitly declared dedicated `selftest` root in an authorized machine manifest (e.g., `X:\<Project>.Perf\config\machine-resources.json`), strictly inside a unique per-run subfolder (`...-run-<guid>`) with cleanup on exit and without traversing junctions or reparse points.
- Never write to arbitrary drive roots, `%USERPROFILE%`, Desktop, Documents, undeclared personal/work OneDrive folders, WSL/UNC media or user network shares (such as `\\rubygloom\Multimedia`), or sibling repositories outside task scope.
- Matching directory names, bare environment variables (`*TEST_ROOT`), or low disk space never grant authorization. Validate the explicit manifest `selftest` root or repository/`.build`/`<Project>.Perf` ownership boundary and fail closed before creating any directory or file.

## Shared-Process Suites

A suite that runs many cases in one process (a self-test executable, a commands suite) proves each case only if every case leaves the process as it found it. The rules (restore and verify state, process-scoped window lookup, quiet baselines before counters, idempotent UI Automation state changes, reproducing order-dependent failures with their predecessor cluster) are in [references/patterns.md](references/patterns.md#shared-process-suites).

## Runs, Receipts, And Qualification

- **Preserve failures.** Keep each fresh run root and every failing run's output; never rerun over a failure before it is recorded.
- **Receipts are source-bound.** A receipt records the source commit, the pins, the toolchain, the binary, and the scenario. Reusing a build (`-SkipBuild`) requires an exact successful receipt for the same source, profile, and artifact.
- **Say what was shown.** Distinguish focused tests, builds, and qualification. A focused pass does not close viewer, interactive, or performance gates, and it is not qualification. Pending CI is an open obligation, never a passed gate.
- **Independent gates.** Native ARM64 execution, sanitizer detection, physical assistive-technology and IME checks, and authorized focus tests are gates of their own; no other result stands in for them.
- **Adding a gate to `test.ps1`.** Add the executable after the existing suites and throw on a nonzero exit. Keep expected-failure children (a probe, an unknown switch) from leaking their exit code into `$LASTEXITCODE`. Record the gate row in the validation contract.

## Performance Evidence

Performance validation is part of the change, never a follow-up task. Use this workflow whenever a change can affect responsiveness, throughput, queueing, rendering, startup, memory retention, or any repeated callback path:

1. **Name the protected scenario**: the exact path being protected. If you cannot name the scenario, you do not yet have a valid performance task.
2. **Choose the metric family**: subsystem-prefixed metric names, and add or reuse instrumentation before claiming results.
3. **Add deterministic validation**: a self-test case or a deterministic harness. If the existing suites do not exercise the scenario, add a focused case instead of relying on a manual repro.
4. **Freeze and measure the instrumented baseline before optimizing**, then measure paired Release latency and memory on a fixed fixture, on the same machine ([performance-resources](../performance-resources/SKILL.md#measurement--non-regression)). Keep submission and GPU-wait diagnostics alongside complete latency and owner CPU cycles. Retain every A/A and A/B slot and every refusal.
5. **Archive the run** in the repository's evidence folder and keep its raw outputs intact.
6. **Report**: the baseline run, the candidate run, the exact metrics that improved or regressed, whether the comparison is same-machine, and any residual blocker. Evidence that is not same-machine or not like for like is directional.
7. **Close out**: if the work completes a WIP plan, move the plan to `Specs/Plans/Done/` and update the authoritative subsystem spec under `Specs/<Domain>/` (or the repository guidance when appropriate); never leave lasting behavior or validation requirements only in the finished plan ([spec-workflow](../spec-workflow/SKILL.md)).

A performance-sensitive change is done when correctness coverage exists, a performance measurement exists, an archived run exists or the block is explicitly documented, and any finished plan is closed out. An unpaired benchmark is diagnostic only and is never a gate. Good metrics and the patterns expected for queue, UI, list, rendering, and storage work: [references/patterns.md](references/patterns.md#performance-metrics).
